# v2.3.0 production verification — later authorization required

No step here authorizes merging to main, deploying, tagging or publishing.
Use a clean GitHub-hosted Ubuntu runner for authoritative HTTP/browser evidence;
local AdGuard rewriting must fail closed and must not change expected headers.

## Before authorized promotion

1. Review/merge the release-readiness PR into `v2.3` only with explicit permission.
   Confirm package/lock root version `2.3.0`, frozen feature scope, no new blockers,
   and green CI/security checks at the final integration SHA.
2. Open/review the dedicated `v2.3` to `main` release PR. Require separate explicit
   merge authorization; never squash/rebase the preserved sprint history.
3. Record the actual resulting **main merge commit** as `RELEASE_SHA`. Do not use
   the integration head or the PR's synthetic test merge as production identity.
   The current workflow automatically deploys main pushes: authorization to
   merge must explicitly account for this deployment trigger.

## Artifact and deployment identity

4. Verify main CI and `Deploy Cloudflare bridge` checkout/build source are
   `RELEASE_SHA`, version `2.3.0`, Node 24, locked dependency inputs and prepared
   asset hashes/licenses. Check the CI-generated record before upload:

   ```text
   schemaVersion = 1
   commit = RELEASE_SHA (40 lowercase hex characters)
   version = 2.3.0
   build.source = github-actions
   ```

   The reviewed candidate archive/digest identifies its own CI build only. A
   later main build has a different source SHA and must be checked again. A ZIP
   digest/source record is not a signed attestation or reproducibility proof.
5. Check isolated deployment output contains `_headers`, `_redirects`, license
   metadata and the full expected site; no CNAME, test/debug/config/agent files,
   TS source/maps, runtime CDN or injected telemetry. Root/generic CNAME must
   remain `securetools.app`; strip only the isolated Cloudflare copy.
6. Record the successful deployment run, GitHub deployment, Cloudflare deployment
   ID and **new immutable URL** from that run. Confirm the expected project,
   canonical custom domain and disabled Web Analytics without changing settings
   as part of verification. Never reuse an old immutable URL as release evidence.

## F-05: live HTTP policy

7. Check canonical `https://tools.securetools.app` and the new immutable origin on
   `/`, `/pdf/merge/`, `/image/to-text/`, `/pdf/to-text/`, `/build-info.json`.
   Use real HTTP responses without redirects/fallback HTML. The existing clean
   browser smoke calls the shared strict `assertSecurityHeaders` validator.
   Require on each document/JSON response:

   - CSP default/script/style/font sources restricted to self; `img-src 'self'
     blob: data:`; `worker-src 'self'`; `connect-src 'none'`; `object-src 'none'`;
     `frame-src 'none'`; `frame-ancestors 'none'`; `base-uri 'self'`;
     `form-action 'self'`.
   - `Referrer-Policy: no-referrer`.
   - `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
   - `X-Content-Type-Options: nosniff`.

   Keep the already-reviewed narrow Tesseract entry-worker header-detach exception;
   do not infer that document CSP may be relaxed. PDF.js retains strict policy.
   Verify canonical indexing remains allowed and pages.dev aliases retain noindex.
