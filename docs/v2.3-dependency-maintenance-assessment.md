# Dependency maintenance assessment — Issue #118

Evidence checked on 2026-10-15 against v2.3 integration commit
`e728eacb4683d42d8c5b1d8a7edf419159096b41`, after merging PR #125.
This is an assessment, not approval to upgrade, patch or replace dependencies.

## Decisions

- **pdf-lib: `INVESTIGATE_REPLACEMENT_IN_V2.4`.** Retain the pinned 1.17.1 for
  v2.3 under current monitoring. The long release gap and uncertain upstream
  response justify a bounded prototype, tracked in [#126](https://github.com/SecureToolsProject/Secure_Tools/issues/126).
  Evidence here does not establish an active exploit requiring replacement
  before v2.3. This is a provisional maintenance decision, not a safety guarantee.
- **JSZip: `DEFER`.** Keep vendored 3.10.1. The 3.10.2 compatibility fixes do not
  justify a patch refresh for the application's current byte-array ZIP writers.
  Revisit if the input boundary, typing needs or advisory evidence changes.

## pdf-lib exposure matrix

All production pdf-lib input loads require `%PDF-` at byte zero. The signature
does not validate structure or constrain the cost of a signature-valid PDF.

| First-party path/tool | Operation and classification | Untrusted PDF parsing? | Security significance |
| --- | --- | --- | --- |
| [Merge](../tools/pdf/merge/pdf.js), its app inspection | Load each source; create destination; copy/reassemble pages | Yes, during inspection and merge | New output does not make copied source objects trusted |
| [Split](../tools/pdf/split/pdf.js), its app inspection | Load source; create/copy selected pages; package generated outputs | Yes | Selection and ZIP generation happen after original parsing |
| [Organizer](../tools/pdf/organize/pdf.js) | Load for page state, reload cached bytes, copy/reorder/rotate retained pages | Yes, including cached reload | Cached bytes remain user input; PDF.js thumbnails are a separate parser |
| [Metadata](../tools/pdf/metadata/pdf.js) | Read Info fields/pages; reload source, delete selected Info entries, save and reparse output | Yes; verification parses a serialized derivative | Metadata-only intent still requires a full PDF parser; this is not arbitrary-content sanitization |
| [PDF to Images](../tools/pdf/to-images/app.js) | `inspectPdf` calls pdf-lib before PDF.js rendering | Yes, despite PDF.js providing the rendering | A replacement assessment must include this preflight dependency |
| [PDF to Text](../tools/pdf/to-text/app.ts), [controller](../tools/pdf/to-text/controller.ts) | `inspectPdf` admission/page count; PDF.js/Tesseract then handle rendering/OCR | Yes in preflight | Plain-text export still exposes pdf-lib even without searchable generation |
| [Searchable PDF](../tools/shared/searchable-pdf.ts) | Load original; embed font; add invisible OCR text; preserve existing pages and save | Yes, then modification of an existing user PDF | Must preserve layout, existing selectable text, annotations and original content |
| [Shared PDF helpers](../tools/shared/pdf.js) | Bounded header read, full read, `PDFDocument.load`, page-count inspection | Yes; common boundary | Catches loading errors/encryption, but does not provide a general parser resource budget |

`PDFDocument.create()` in Merge/Split/Organizer creates a new destination, but its
page sources are untrusted. There is no separate production pdf-lib-only path
creating a PDF solely from trusted generated data. Images to PDF uses **jsPDF**,
not pdf-lib. PDF.js rendering and Tesseract recognition are separate dependencies.

Tests invoke pdf-lib to make synthetic fixtures, reload outputs and inspect
regressions: `pdf-merge-and-categories`, `pdf-split`, `pdf-organizer`, `pdf-metadata`,
`pdf-signature`, and `searchable-pdf` tests; browser `gate-fixtures`, `pdf-ocr-smoke`
and `release-hardening`; production `fixtures.mjs` and `pdf-artifact.mjs`; and the
`verify-browser-export-artifacts`/`verify-hardening-download` diagnostic scripts.
These are testing/operator parsing surfaces, not additional public app routes.
Build/deployment scripts copy or check assets; `prepare-searchable-pdf-assets.mjs`
prepares **fontkit/fonts**, not a pdf-lib parsing job. A deployment smoke asset
reference by itself is not a parser invocation.

## Upstream maintenance and security evidence

The [npm registry](https://registry.npmjs.org/pdf-lib) and
[GitHub release](https://github.com/Hopding/pdf-lib/releases/tag/v1.17.1) still
identify 1.17.1, published 2021-11-06, as the latest original release. The
[repository API](https://api.github.com/repos/Hopding/pdf-lib) reports not archived
and last push 2024-07-17. Its [default-branch commits](https://github.com/Hopding/pdf-lib/commits/master/)
still end at `93dd36e85aa659a3bca09867d2d8fac172501fbe` (2021-11-12).
Repository `updated_at`, new issue comments and recent community PR submissions
do not establish recent maintainer code/release activity.

The contributor API shows historical concentration: Hopding has 358 commits
versus 13 for the next listed contributor (a bot). This does not establish current
permissions, staffing or a response guarantee. The original
[maintainership guide](https://github.com/Hopding/pdf-lib/blob/master/docs/MAINTAINERSHIP.md)
describes an unpaid principal maintainer and stale-issue closure; it is historical
policy, not evidence that its old response targets are met today. Describe the
original project as **low release/code activity with uncertain response**, rather
than asserting abandonment or treating it as merely stable because no release is new.

Exact-input OSV checks for pdf-lib 1.17.1 returned no known advisories at this
verification time. Its [public repository advisories](https://github.com/Hopding/pdf-lib/security/advisories)
were empty. This is not a comprehensive CVE search or proof of parser safety.
Public [report #1776](https://github.com/Hopding/pdf-lib/issues/1776) and
[PR #1781](https://github.com/Hopding/pdf-lib/pull/1781) concern XRef parsing.
The report was closed by the stale bot, not by a verified fix; the PR is open with
no reviews. Its impact claims were **not independently reproduced or accepted as
a confirmed vulnerability** here. Do not equate its closure with remediation, or
repeat its native-memory-corruption claims as established JavaScript behavior.
This is a concrete triage/response uncertainty, not a release-blocking exploit finding.

### What existing defenses do and do not cover

| Control | Material benefit | Remaining boundary |
| --- | --- | --- |
| Five-byte admission | Rejects empty, spoofed and incomplete-header input before full read/parser entry | Any signature-valid malicious structure still reaches the parser |
| Parser errors and encrypted-input rejection | Stops supported failures from producing successful results | Cannot catch an allocation spike or work that never completes; parsers can repair/tolerate some malformed input |
| Render limits, sequential OCR and cleanup | Bounds raster dimensions/pixels and some concurrent work; cancellation suppresses obsolete results | These are **not** universal pdf-lib file/page/time/memory caps or a hard abort of every `load()`; loading currently occurs in the page context |
| Browser-local processing, no backend | No service-side parser/file-upload attack surface | Browser CPU/memory and origin trust still matter; local-only is not parser isolation |
| Strict document CSP | Restricts code/resource/network behavior | Not a parser correctness or resource-consumption proof; integrated HTTP header delivery still awaits release verification |
| Hash pins, corpus and CodeQL/advisory checks | Detects changed approved bytes, regressions and known/pattern-based issues | Pins retain old bugs; CodeQL excludes vendored bundles; nested/native dependency coverage remains incomplete |

No universal parser budget is claimed. A future prototype must evaluate hard
termination/resource controls, not assume an async API or a newer engine supplies them.

## Browser-local fallback comparison

The byte counts below were measured from current vendored files or npm package
archives whose SHA-512 matched registry integrity. Candidate archives were read
in memory, **not installed or executed**. Gzip uses level 6. Figures exclude
separate fonts/fontkit, runtime initialization and other app assets, and are not
whole-app download or memory benchmarks.

| Candidate | Browser-local / features | Measured bundle cost | WASM/native complexity | Maintenance / migration risk |
| --- | --- | --- | --- | --- |
| Retain pdf-lib 1.17.1 temporarily | Existing complete editor/generator integration | 525,099 B JS; 206,639 B gzip | None | Lowest immediate regression risk; poor original release cadence, current parser exposure remains |
| [Cantoo fork](https://github.com/cantoo-scribe/pdf-lib), npm `@cantoo/pdf-lib` 2.11.1 | Publisher claims original APIs plus editing/font/form features; closest adapter candidate | 616,746 B minified JS; 251,781 B gzip, before fontkit/fonts | None for base library | Recent default-branch work/tag v2.11.0 on 2026-09-11; product-focused support, broader behavior must be tested; provenance discrepancy below blocks blind adoption |
| [PDF.js](https://mozilla.github.io/pdf.js/) | Already used for parse/render/text extraction; possible reuse for renderer-backed preflight | Already vendored: 454,669 B JS + 1,262,398 B worker; 505,270 B combined gzip | Existing JS worker | Maintained renderer; **not a drop-in page-copy/Info-cleaning/font-writing editor**. Save/annotation support does not prove required editing coverage |
| [MuPDF.js](https://github.com/ArtifexSoftware/mupdf/blob/master/platform/wasm/README.md), npm mupdf 1.28.1 | Official browser-capable bindings; page manipulation/editing/rendering | 10,409,826 B WASM + 132,111 B JS; about 4.74 MB combined gzip | High: WASM lifecycle, memory, workers and native dependencies | Active native project; major API/behavior migration. Apache-2.0 is the package's declared license |

Cantoo's [publisher README](https://github.com/cantoo-scribe/pdf-lib#readme) claims
API continuity and additional repair/format behavior; that is not Secure Tools
compatibility evidence. Registry latest is 2.11.1 (2026-09-15), while observed
repository tags/default branch end at v2.11.0. The registry's 2.11.1 gitHead
`c8c88e84dcd5510ec35921123bb5140fe02a7115` could not be resolved in its declared
repository (HTTP 422); the v2.11.1 ref returned 404. Reconcile that provenance or
select another auditable exact version before prototyping. This discrepancy does
not itself establish compromise. Its inherited maintainership guide also must
not be mistaken for a verified current staffing/SLA statement.

Custom byte rewriting is not a serious general PDF editing replacement. Keep the
existing narrow signature check; do not invent a second PDF parser for metadata
removal or page copying. No candidate has been demonstrated to eliminate current
risks. A small adapter/corpus prototype is preferable to replacing all paths at once.

## JSZip 3.10.2 relevance

The [tag comparison](https://github.com/Stuk/jszip/compare/v3.10.1...v3.10.2)
contains eight commits, including the three compatibility changes described by
the [changelog](https://github.com/Stuk/jszip/blob/v3.10.2/CHANGES.md). The registry
published 3.10.2 on 2026-09-08 UTC; the changelog dates it September 9. The tag
exists, but the repository release-by-tag API returned 404: absence of a GitHub
Release object is not absence of the npm/tagged version.

| Change | Actual Secure Tools boundary | Decision |
| --- | --- | --- |
| Cross-realm Array/ArrayBuffer/Uint8Array detection | Three writers: [image-output](../tools/shared/image-output.js) for Converter/Resize/Compressor, [PDF Split](../tools/pdf/split/pdf.js), and [PDF to Images](../tools/pdf/to-images/converter.js). They insert local Uint8Arrays; Blob-based images are converted via `arrayBuffer()` and a new local typed array. No foreign-window/iframe archive input was found | Binary detection is exercised, but not the foreign-realm case fixed by the patch |
| Missing `JSZip.defaults` TypeScript declarations | ZIP helpers are JS, no defaults API use or JSZip TS import was found | No current type-check benefit demonstrated |
| Node 18+ Blob input | Production creates browser ZIPs. Node verification reads generated bytes/ArrayBuffers; app helpers convert input Blobs to typed arrays before `.file()` | Could help a future direct Node Blob tool; does not repair current app behavior |

One-off Node 24 checks confirmed current 3.10.1 round-trips local typed-array input,
while direct Node Blob insertion fails. That unsupported test-only boundary is
not used by today's helpers. Existing Split/To-Images ZIP regressions passed.
Production writes archives; `loadAsync` usage is test verification, not a user ZIP
import feature. No JSZip advisory fixed specifically by 3.10.2 was identified in
the inspected changelog/public advisories, and current exact-input OSV returned
no known advisory. Do not infer that no undisclosed vulnerability exists.

## Future change plan — not implemented

For a separately approved JSZip update: acquire the exact registry artifact;
verify package integrity and the selected MIT license; replace vendored JS,
package metadata and README provenance; update approved version/hash in
`config/security/vendor-release-pins.json`; rerun inventory consistency, release
and ZIP tests (including version-specific expectations), then full browser/native
download checks. JSZip is **not currently a root npm/lockfile dependency**: do not
invent a lockfile bump or add it solely for this assessment. If future vendoring
automation introduces it as a build input, update package.json/lockfile together
in that reviewed task. The security manifest resolves metadata versions; it has
no duplicate version field to bump. Add foreign-realm/Node Blob cases only if
those boundaries become supported requirements.

For the v2.4 pdf-lib prototype in #126:

1. Reconcile candidate release/tag/commit/artifact/license and nested-dependency
   provenance; compare against current behavior through an adapter.
2. Consider reusing PDF.js inspection first only on already renderer-backed
   Images/Text paths; then test Merge/Split/Organizer, Info metadata, and finally
   Searchable PDF separately. Avoid adding redundant parsers to every tool.
3. Use classic/object-stream PDFs, rotations/crop boxes, forms, annotations,
   bookmarks, empty/encrypted/truncated/malformed cases, large/deep structures,
   and bounded isolated evaluation of public parser reports. Preserve error
   categories and intentional rejection behavior; don't silently accept more
   repair-tolerated content.
4. Compare page count/order/geometry, metadata field semantics, links/forms,
   extraction and original rendered pixels. Test Korean/English font subsetting,
   OCR line geometry, and no duplicated existing selectable text. Serialized byte
   equality is not required because IDs/compression/serialization can change.
5. Measure input size/page budgets, mobile latency, peak memory, cancellation and
   hard parser termination in an isolated worker/process, with no network/file
   upload or CSP weakening. Benchmark rather than assume better performance.
6. Only after a review decision, update tool adapters, vendoring/provenance,
   canonical pins/licenses/security inventory, regressions and complete browser
   gates in a focused implementation PR. No such implementation is authorized here.

## Review triggers and release/UX boundary

Reassess immediately on a relevant advisory or reproducible security failure,
upstream archival, a required feature that cannot be maintained, or stronger
evidence of parser bugs without a response. Recheck before v2.3 promotion.
Current prolonged inactivity and unresolved-report triage already justify #126;
an auditable, compatible maintained successor is another selection trigger.

The audit backlog is sufficiently addressed to **begin a separately authorized
v2.3 UX/mobile pass**, under the existing policy permitting nonblocking P1/P2 work.
This is not production GO or a declaration that the audit is fully closed:
F-02 default-branch automation, F-04 nested/native coverage, and F-05/F-06 live
delivery/provenance evidence remain outstanding. Any newly confirmed P0 overrides
that development readiness. No UX work starts in this assessment.
